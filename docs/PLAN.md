# 计划 V3：先定平台，模型待定

目标：**≤500MB、纯 CPU 可跑、拷到另一台电脑双击即用的绿色包。**

---

## 1. 平台候选（只评平台）

| 平台 | 形态 | 运行时体积 | CPU | 自带服务 | 再分发 | 判断 |
|---|---|---|---|---|---|---|
| **llama.cpp** | 单目录 + exe | **62 MB（实测）** | 按微架构拆 DLL，自动选 | ✅ OpenAI 兼容 | MIT | ✅ 首选 |
| **llamafile** | **单个 exe（模型内嵌）** | 模型 + ~20 MB | 仅 CPU | ✅ 有 server | Apache-2.0 | ✅ 备选，最像"一个安装包" |
| Ollama | 安装器 + 后台服务 | ~1 GB | CPU/GPU | ✅ | MIT | ❌ 要安装，不够绿 |
| ONNX Runtime | 库，无服务 | ~15 MB | ✅ | ❌ 要自己写 | MIT | △ 适合专用 NMT |
| CTranslate2 | 库（Python/C++） | ~30 MB | ✅ 极快 | ❌ 要自己写 | MIT | △ 只适合专用 NMT |
| wllama / WASM | 浏览器内 | 0 | ✅ 但慢 5–10× | ❌ | MIT | ❌ 500MB 跑不动 |

**推荐 llama.cpp**，四个理由：

1. 单目录、无安装、无注册表，官方 zip 解压即用
2. 同一套 GGUF 通吃 CPU / GPU，换机器不用换模型
3. `llama-server` 自带 OpenAI 兼容接口，自有 app 直接调，不用再写网关
4. 刚发布 **v1.0.0（2026-11-13）**，公共 API 稳定，不再是天天变的 nightly

**llamafile 作为备选**：把模型和运行时打成一个 exe，最贴合"一个安装包拷过去"，但只能 x86_64 + CPU，且一个模型一个文件。

## 2. 真正的平台问题：绿色化的三个细节

选运行时只是第一步，能不能"任意机器跑"取决于这三点：

| # | 问题 | 影响 | 解法 |
|---|---|---|---|
| a | **CPU 指令集** | 老机器没有 AVX2 | **已解决**：build 12359 把 CPU 后端拆成 `ggml-cpu-*.dll`（sandybridge→sapphirerapids，外加 `x64`/`sse42` 基线），运行时自动挑，**不需要两套 exe** |
| b | **VC++ 运行库** | 干净系统缺 `vcruntime140.dll` | 实测官方包不含 vcruntime，需在干净机确认；缺则附 dll |
| c | **路径与配置** | 用户目录/中文/空格路径、注册表、AppData 残留 | 全部相对路径 + 一个 `config.json`；不写注册表、不写 AppData |
| d | **中文脚本编码** | PS 5.1 按 GBK 读无 BOM 的 .ps1，中文全乱、直接语法错 | `.ps1` 一律存 **UTF-8 with BOM**（已踩过） |

这三条不解决，"拷贝即用"就是空话。

### 2.1 GPU：不做厂商分支，做一个通用后端

| 后端 | 覆盖 | 体积 | 定位 |
|---|---|---|---|
| **CPU** | 所有 x64 | 已含 | **必选**，永远能跑 |
| **Vulkan** | N 卡 / A 卡 / I 卡 | +20–40 MB | 通用加速，一个 exe 通吃三家 |
| CUDA | 仅 NVIDIA | +500 MB～1 GB | 可选下载，不随包 |
| HIP / ROCm | 部分 A 卡 | 大 | 不用（Windows 上挑卡且不稳） |
| SYCL | Intel | 大 | 不用（要 oneAPI 运行时） |
| Metal | Apple | 已含 | macOS 版再说 |

关键判断：**Vulkan 的运行库随显卡驱动自带**，不需要额外打包；而 CUDA 的运行库要自己带，这正是它体积大的原因。

启动探测顺序 → `NVIDIA?` 提示 CUDA 包 ／ `Vulkan?` 直接用 ／ 都没有 → 静默 CPU。

补充一个反直觉的结论：**这个体量的模型，CPU 已经够快**（内存带宽受限，短句几百毫秒）。GPU 收益主要在长文本、批量、连续划词。所以 GPU 是选修课，不能为了它牺牲"任意机器"这条主线。

### 2.2 模型目录：可插拔，不写死

```
translate-ai\
├─ llama-server.exe
├─ models\
│  ├─ bundled-q4.gguf        ← 自带（≤470MB）
│  └─ *.gguf                 ← 用户丢进来的任意模型
├─ config.json               ← {"model": "models/bundled-q4.gguf", "n_ctx": 4096}
└─ 启动.cmd
```

规则：

1. 启动扫 `models/*.gguf`，全部列出来；**代码里不出现任何模型文件名**
2. config 指定的不存在 → 回退目录里第一个；目录为空 → 提示放模型，不崩
3. 切换模型 = 改 config 或界面选择 → 重启 server 进程（1–3 秒），不做多模型常驻（省内存）
4. 路径全部相对，整个文件夹搬走仍可用

四个必须处理的坑：

| 坑 | 后果 | 处理 |
|---|---|---|
| 用户丢进来的 GGUF 架构不被当前构建支持 | 加载失败 | 先校验 GGUF 头 + 架构名，不支持就标"不兼容"，别让进程崩 |
| 模型自带 128k 上下文 | 吃光内存 | `n_ctx` 由 config 强制覆盖（默认 4096） |
| 聊天模板千奇百怪 | 译文质量骤降 | 翻译走固定 prompt，必要时用 `--chat-template` 覆盖，不信任模型自带模板 |
| 同名/嵌套目录 | 选错模型 | 只扫一层 `models/*.gguf`，用文件名当 ID |

- 审计日期：2026-11-18
- 审计人：lead（DSH agent）

## 0. 结论摘要（TL;DR）

| 问题 | 结论 |
|---|---|
| 有没有现成项目能直接用？ | **桌面端有，服务端没有。** STranslate（MIT、活跃、Windows）内置 `127.0.0.1:50020` HTTP API，配 Ollama 本地模型即可覆盖"划词 / 输入 / 截图 OCR"；但它 Windows-only，且没有稳定可移植的服务契约。 |
| 最像"全包"的项目？ | Pot（19.3k★），自带 `60828` HTTP API 且内置 `/selection_translate`、`/input_translate`——**但整个组织已归档（archived），2026-07 后停更**，不能作为长期底座。 |
| 需要自己缝吗？ | **需要，但只缝一层薄的。** 缝的是"翻译服务层"（OpenAI 兼容 + 术语表 + 分段 + 缓存），不是模型、不是推理、不是取词底层。 |
| 推荐路线 | **B 方案：STranslate 当日常壳 + Ollama/llama.cpp 当推理 + 自建 300 行网关当契约层。** 今天可用，1–2 天可接入自有 app，可移植。 |
| 最大硬约束 | RTX 3050 **6GB 显存** → 7B 模型是"能跑但贴边"，1.8B 才是舒适区。 |
| 最大非技术风险 | 腾讯混元社区许可证（排除 EU/UK/KR、MAU 门槛）；HF 直连不可用（实测），必须走 hf-mirror / ModelScope。 |

## 1. 需求拆解

原话："本地部署一个 AI 用于日常翻译，接入自己开发的 app，支持划词翻译、输入翻译，还可以无痛移植。"

翻译成可验收的技术需求：

| 编号 | 需求 | 可验收标准 |
|---|---|---|
| R1 | 本地推理、离线可用、数据不出机 | 断网后功能不降级；无出站请求（可用抓包验证） |
| R2 | 日常交互：划词、输入、截图/OCR、剪贴板 | 全局热键 → 500ms 内出弹窗；划词在 Word/Chrome/PDF 阅读器可用 |
| R3 | 可编程接入自有 app | 稳定 HTTP 契约 + 流式；错误码明确；有 SDK 片段 |
| R4 | 无痛移植 | 换机/换人：解压即用，无 Docker、无管理员、无 Python 环境；模型可换下载源 |
| R5 | 质量与延迟平衡 | 划词首字 < 800ms；中英短句质量 ≥ 免费云翻译；术语可控 |

**"无痛移植"是歧义项，本审计按三种可能解读分别覆盖：**

1. **从云 API 无痛迁移到本地** → 用 OpenAI 兼容接口，业务代码零改动（§5.3）
2. **换机器/给别人装无痛** → llama.cpp 便携二进制 + GGUF + 单文件网关（§5.4）
3. **移植进自有 app 代码** → 契约层 + 各语言调用片段（§5.3）

### 2.1 显存可行性测算（关键）

按 GGUF Q4_K_M + 2–4k 上下文估算（权重体积取自 Ollama 模型页实测值）：

| 模型 | 权重 | KV+计算缓冲 | 峰值估算 | 6GB 可用性 | 预期速度* |
|---|---|---|---|---|---|
| HY-MT1.5-**1.8B** Q4_K_M | 1.1 GB | ~0.5 GB | **~1.6–2.0 GB** | ✅ 舒适，可与桌面共存 | ~80–120 tok/s |
| Qwen3-4B 级 Q4_K_M | ~2.5 GB | ~0.8 GB | ~3.3–3.6 GB | ✅ 可用 | ~40–60 tok/s |
| HY-MT1.5-**7B** Q4_K_M | 4.6 GB | ~0.8–1.2 GB | **~5.4–6.2 GB** | ⚠️ 贴边，桌面占显存即触发共享内存（速度骤降） | ~20–30 tok/s |

| 14B+ | ≥8 GB | — | 溢出 | ❌ 不可行 | — |

### 3.4 取词层（"划词"到底怎么实现）

三条路，生产上要**三层回退**：

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| ① 辅助功能 API | Windows UIA `TextPattern` / macOS AX / Linux AT-SPI | 不碰剪贴板、不打断用户 | Electron/Chrome/部分 PDF 阅读器拿不到选区 |
| ② 模拟复制 | 发 Ctrl+C 读剪贴板后**还原** | 兼容性最好 | 会污染剪贴板；需做"不打扰复制"（保存/恢复） |
| ③ 截图 OCR | `Windows.Media.Ocr`（离线）/ PaddleOCR / RapidOCR | 图片、扫描件、游戏都能取 | 慢 200–500ms；有识别错误 |

参考实现：[dsh-translate](https://github.com/Azurwolf1024/dsh-translate)（MIT，2026-11 新建，1★）已把"UIA → 剪贴板 → OCR"三层回退和浮窗贴选区做完，可直接读源码抄思路（**新项目、低采用度，只当参考不当依赖**）。

## 5. 推荐架构（B 方案）

### 5.1 进程拓扑

```
┌──────────────────────────────────────────────────────────────┐
│ Windows 桌面                                                  │
│                                                              │
│  [取词源]                      [日常壳]                       │
│   UIA / 剪贴板 / OCR  ───────▶  STranslate (50020)            │
│        │                          │  划词/输入/截图/OCR/TTS    │
│        │                          ▼                          │
│        │                    ┌───────────────┐                │
│        └───────────────────▶│  翻译网关      │  :8787         │
│         (自有 app 直接调)     │  OpenAI 兼容   │                │
│                              │  术语表/分段/缓存│               │
│                              └───────┬───────┘                │
│                                      │ /v1/chat/completions    │
│                              ┌───────▼───────┐                │
│                              │ Ollama :11434 │ 或 llama-server │
│                              │ HY-MT1.5-1.8B │  (便携 CUDA)    │
│                              └───────────────┘                │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 推理后端 | **Ollama（开发期）/ llama.cpp `llama-server`（发布期）** | 两者都 MIT、都 OpenAI 兼容；llama-server 是单文件，最符合"无痛移植" |
| 默认模型 | **HY-MT1.5-1.8B**，7B 为可选质量模式 | 6GB 显存现实（§2.1） |
| 契约 | **OpenAI `/v1/chat/completions` 为唯一主契约**，`/translate` 为便捷封装 | 业务代码可一行切换云/本地；迁移成本≈0 |
| 网关语言 | Node 24（零依赖单文件）或 Go（单 exe） | 本机已有 Node；Go 更适合发给别人（二选一，见 §10-Q3） |
| 取词 | 先借 STranslate；自有 app 需要时再实现三层回退 | 不重复造轮子 |
| 端口安全 | 全部 `127.0.0.1` 绑定；非回环必须 API Key | 防止局域网被白嫖/投毒 |

### 5.3 契约草案（网关）

```
POST /v1/chat/completions        # OpenAI 兼容，SSE 流式；模型名映射到本地
POST /translate                  # {"text","from","to","glossary_id?","style?"} → {"text","segments[]","ms"}
GET  /health                     # {"ok":true,"backend":"ollama","model":"hy-mt1.5-1.8b","vram_mb":1820}
GET  /models                     # 已加载/可选模型
POST /glossary                   # 术语表 CRUD（对应混元的"术语干预"提示模板）
```

内部固定使用混元官方提示模板（**这决定了输出质量，别自创**）：

- 中↔外：`将以下文本翻译为{目标语言}，注意只需要输出翻译后的结果，不要额外解释：\n\n{原文}`
- 外↔外：`Translate the following segment into {target}, without additional explanation.\n\n{src}`
- 术语干预：`参考下面的翻译：{src_term} 翻译成 {dst_term}` + 上述模板
- 采样参数（官方推荐）：`top_k=20, top_p=0.6, repetition_penalty=1.05, temperature=0.7`

**长文本策略**：按段切分（≤400 字/段）→ 并发 2–4 路 → 拼接；**不要**整篇塞进 1.8B（会漏译、串行）。

### 5.4 "无痛移植"交付物

```
translate-ai/
├─ runtime/llama-server.exe        # MIT，CUDA 便携版，无需安装
├─ models/hy-mt1.5-1.8b-q4_k_m.gguf  # 1.1GB，随包或首启下载
├─ gateway/translate-gateway.exe   # 自建，单文件
├─ config.json                     # 唯一配置：端口/模型/术语表路径/上游地址
└─ start.cmd                       # 双击即用：起服务 + 开 STranslate
```

- 模型分发：优先 **ModelScope / hf-mirror**（实测可达），Ollama 用户可直接 `ollama pull demonbyron/HY-MT1.5-1.8B`
- 不做 Docker（本机没有，且给普通用户装 Docker 是反"无痛"的）
- 配置里 `backend` 三选一：`ollama | llamacpp | openai-compatible`，换机器只改这一行

## 7. 验收标准与基准测试计划

**M1 验收（当天）**
- `curl 127.0.0.1:50020/translate -d "Hello world"` 返回中文
- 断网后划词仍可用
- `nvidia-smi` 显存峰值 < 2.5GB（1.8B）

**M2 验收（网关）**
- `POST /v1/chat/completions` 支持 SSE，首 token < 400ms（短句）
- 术语表命中率 100%（给定 20 条术语）
- 500 字文本分段翻译，无漏段、无重复

**质量基准（关键，别跳过）**
1. 自建 50 句集：中→英、英→中各 25 句，含 5 句长难句、5 句带术语
2. 四个选手：1.8B / 7B / Qwen3-4B / 免费云 API（基线）
3. 盲评 3 维度：准确性、流畅度、术语一致性（1–5 分）
4. 记录：首字延迟、总耗时、显存峰值
5. **通过线：1.8B 综合 ≥ 云基线 -0.3 分，且首字 < 800ms**

## 11. 决策记录（2026-11-18，据用户答复修订）

用户答复：
- Q1 自有 app = **还没开始，就在 `translateAI` 里新建**
- Q2 平台 = **Windows + macOS + Linux**
- Q3 用途 = **分发给他人（非商用）**

这三条推翻了 §4 里 B 方案的一个前提（"借 STranslate 当壳"），因此修订如下。

### 11.1 影响一：壳必须自研，STranslate 降级

跨平台 + 分发 ⇒ Windows-only 的 WPF 壳不可用。STranslate 的身份从"方案主体"降为：

- **Windows 上的可选加速器**（自己先用着，验证需求）
- **参考实现**（它的服务适配器模式、50020 契约、插件市场，值得读源码）

主路径变为：**自研跨平台壳 + 自建网关 + 内置 llama-server**。

### 11.2 影响二：模型许可从"注意"升级为"红线"

分发混元权重会同时踩两条：**地域排除 EU/UK/KR** + **需随附许可证/NOTICE**。非商用不等于免责。

**修订策略：不随包分发任何权重。** 首次启动走"模型向导"：

| 选项 | 模型 | 许可 | 说明 |
|---|---|---|---|
| 默认 | Qwen3-4B（Q4_K_M，~2.5GB） | Apache-2.0 | 可自由分发/商用，6GB 显存可用 |
| 推荐 | HY-MT1.5-1.8B（Q4_K_M，1.1GB） | 腾讯混元社区许可 | 质量更好，**由用户自行下载**，界面明示地域与商用限制 |
| 兜底 | opus-mt / NLLB | CC-BY / CC-BY-NC | 极快、极省，质量低 |

权重由用户机器在向导里从 ModelScope / hf-mirror 拉取，你的安装包不含模型文件——**既避开再分发条款，也把安装包从 1GB+ 压到 10MB 级**。

### 11.3 影响三：壳选型（新增决策）

| 维度 | Tauri 2 | Electron | Qt 6 |
|---|---|---|---|
| 安装包体积 | 8–15 MB | 90–150 MB | 20–40 MB |
| 与你现有栈的匹配 | 需装 Rust（本机无 cargo） | Node 24 已就绪 | Qt 5.14 已有，需升 6 |
| 取词原生能力 | Rust crates：`windows` / `accessibility` / `atspi` | 依赖 native 模块，跨平台较脆 | **最直接**：COM UIA / AXUIElement / AT-SPI |
| 跨平台一致性 | WebView2 / WKWebView / WebKitGTK，有差异 | 自带 Chromium，最一致 | 原生控件，各自平台观感 |
| 分发省心度 | 高 | 中（体积） | 高（Linux 需处理依赖） |

**推荐 Tauri 2**：体积对"发给别人"这件事是决定性的；Rust 侧正好承载三平台取词，Web 侧做 UI 迭代快。代价是要先装 Rust 工具链（~1.5GB）。

若想最快出可分发版本，退而求其次选 **Qt 6**（取词最省事、单 exe、你已有 C++ 底子），UI 用 QML。

### 11.4 修订后架构（B'）

## 12. 反面需求：Pot 实测痛点 → 设计约束（2026-11-18 追加）

用户原话：

> "他没有本地模型的功能，划词使用的外部 google 等翻译 api 应该是，所以经常只有一个网络服务可用还经常翻译不准，截图翻译几乎每次都识别错误文字导致无法翻译。"

外加多选：**慢/首字延迟高、界面丑不可定制、缺功能（术语表/格式/对比）、整体手感不对**。

这条反馈修正了 §3.1 的判断：**Pot 的"形态贴合"只说明交互范式对，不说明能力达标。** 它的两个核心短板恰好是日常使用中最致命的。

### 12.1 痛点 → 硬指标

| # | 痛点 | 设计约束 | 技术手段 | 验收 |
|---|---|---|---|---|
| P1 | 没有本地模型，全靠外部 API | **本地模型是默认路径，不是可选项** | 首启向导 3 步装好；模型常驻预热；断网可用 | 拔网线后划词/输入/截图全部可用 |
| P2 | 免费接口只剩一个能用，且不稳 | **离线优先 + 多后端故障转移** | 本地为主，云为可选备用；后端健康探测 | 任一后端挂掉不影响使用 |
| P3 | 翻译不准 | **专用翻译模型 + 术语表 + 可对比** | HY-MT1.5 / Qwen3-4B；术语干预；多引擎并排 | 50 句盲测 ≥ 云基线 −0.3 |
| P4 | **截图 OCR 几乎每次都错** | **OCR 是一等公民，P0** | RapidOCR(PP-OCRv5) 默认；小图 2× 上采样；方向分类；VLM 兜底 | 真实截图 30 张，整行通过率 ≥95% |
| P5 | 慢、首字延迟高 | 常驻 + 流式 + 小模型 | 1.8B/4B 常驻显存；SSE 流式；预热请求 | 划词首字 < 800ms |
| P6 | 界面丑、不可定制 | 极简原生、主题/字体/快捷键全可配 | 壳层自绘浮窗，不抢焦点 | 3 套主题 + 全部快捷键可改 |
| P7 | 缺术语表/格式/对比 | 术语表、格式保留、多源并排 | 混元术语模板；<sn> 标签格式保留 | 20 条术语 100% 命中 |
| P8 | 手感不对 | 不打断：贴选区、Esc 即消、键盘优先、绝不抢焦点 | 浮窗 `WS_EX_NOACTIVATE` / NSPanel nonactivating | 连续划词 20 次无焦点丢失 |

### 12.2 为什么 OCR 必须重做（P4 拆解）

"几乎每次都识别错"通常不是单一原因，而是四个坑叠加：

1. **引擎选错**：Pot 在 Windows 上走 `Windows.Media.Ocr` 或 Tesseract。前者中文精度一般且依赖语言包，后者对中英混排的小字几乎不可用。
2. **缩放丢失细节**：HiDPI 截屏后若被降采样，10px 的中文字直接糊成一片，OCR 再强也救不回。
3. **没有方向/版面分析**：斜排、竖排、多栏时行切分错乱，译文顺序全乱。
4. **整屏识别而非选区识别**：背景噪声、图标、边框被当成文字。

对应的工程答案（按性价比排序）：

| 手段 | 收益 | 成本 |
|---|---|---|
| **RapidOCR (PP-OCRv5, ONNX)** 替换系统 OCR | 中英混排准确率大幅提升，CPU 100–300ms，模型 ~20MB | 低（一行依赖） |
| 小图 **2× 上采样** + 灰度/对比度预处理 | 小字号精度显著提升 | 极低 |
| 方向分类 + 行合并 | 竖排/斜排可用 | 低 |
| 只识别选区、忽略边框 | 减少噪声 | 低 |
| VLM OCR（Qwen3-VL-2B）兜底 | 复杂版面/手写可用 | 中（占显存，仅兜底） |

> 结论：**RapidOCR 作为默认引擎，Windows OCR 仅作兜底，VLM 作为"疑难件"可选**。这一条如果做不到，其他功能做得再好用户也不会用——这正是 Pot 的教训。

### 12.3 修订 M0：先用两个实验证明短板被补齐

原 M0（写网关）推迟，改成**先做两个对照实验**，因为它们决定项目值不值得继续：

**实验 A — OCR 对照（半天）**
- 素材：你自己的 30 张真实截图（含小字、中英混排、深色模式、PDF 阅读器）
- 选手：Pot 内置 OCR / Windows.Media.Ocr / **RapidOCR**
- 指标：字符准确率、整行通过率、耗时
- 通过线：RapidOCR 整行通过率 ≥95%，且比 Pot 高 ≥15 个百分点

**实验 B — 翻译对照（半天）**
- 素材：20 句真实工作文本（不是新闻稿）
- 选手：Google（你现在用的）/ HY-MT1.5-1.8B / Qwen3-4B
- 指标：准确、通顺、术语一致（1–5 分盲评）+ 首字延迟
- 通过线：HY-MT 综合 ≥ Google，且首字 < 800ms

**两个实验都过 → 按 §11.5 继续；任一不过 → 先解决那一项，别急着写壳。**

### 12.4 对 §4 打分的修正

| 方案 | 原 R2 | 修正后 | 原因 |
|---|---|---|---|
| Pot | 5 | **3** | 用户实测：本地模型不可用、OCR 不可用 |
| STranslate | 5 | **4（待实测）** | 内置微信 OCR，中文通常优于 Pot，但需用实验 A 验证 |
| 自研 | 3 | **3（目标 5）** | 正因为前两者都不达标，自研的必要性从"想要"变成"必须" |
